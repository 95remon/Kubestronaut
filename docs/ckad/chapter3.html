🚀 المهمة 3: الإعدادات

Configuration

الدرس 1

🛸 الأوامر في دوكر (Docker Commands & Arguments)

يا كابتن! 🧑‍🚀 قبل ما نطلع بمركبة كوبرنيتس، لازم نفهم المحرك بتاعنا (Docker) بيشتغل إزاي من جوه. تحديداً، إزاي بنقول للكبسولة تعمل إيه لما تشتغل، وإمتى بتقف؟

🌌 الفكرة ببساطة

الكبسولة (Container) في دوكر مش زي السيرفر العادي (VM) اللي بيفضل شغال على طول. الكبسولة دي تخصص! بتصحى تعمل مهمة محددة ولما تخلصها... بتموت (Exit). 💀

🛸 تشبيه الفضاء

تخيل الكبسولة زي الصاروخ. مهمته يوصل قمر صناعي للمدار. بمجرد ما يوصله، مهمته انتهت والمحركات بتقف. لو حاولت تشغله من غير ما تقول له رايح فين (Command)، مش هيتحرك!

🏃‍♂️ تجربة عملية: Ubuntu Container

تعالى نجرب نشغل كبسولة ubuntu. لو كتبت الأمر ده:

docker run ubuntu

هتلاحظ إنها اشتغلت وقفلت في نفس اللحظة! ليه؟ 🤔
عشان ubuntu بطبيعتها نظام تشغيل، لو مشغلتش عليه برنامج (زي Bash)، ملوش لازمة فبيعمل Shutdown فوراً.

🔧 الفرق بين CMD و ENTRYPOINT (مهم جداً!)

في ملف الـ Dockerfile، عندنا أمرين بيحددوا الكبسولة هتعمل إيه:

  • CMD: ده الأمر الافتراضي. ممكن تغيره وأنت بتشغل الكبسولة. (زي اقتراح من السيستم)
  • ENTRYPOINT: ده الأمر الأساسي اللي لازم يشتغل. أي حاجة تكتبها بعده بتعتبر تكملة ليه (Arguments). (زي أمر عسكري)
💡 نصيحة من الكابتن

لو عايز تعمل كبسولة بتنام (Sleep) لمدة معينة، استخدم ENTRYPOINT ["sleep"] وخلي الثواني في CMD ["5"]. كده لو حد شغلها من غير ما يكتب حاجة، هتنام 5 ثواني. ولو كتب 10، هتنام 10!

🔧 ركن القيادة — مصطلحات

Original Title: Commands and Arguments in Docker
CMD: Command instruction (Default args)
ENTRYPOINT: The main executable of the container

الدرس 2

🛸 الأوامر في كوبرنيتس (Commands in K8s)

دلوقتي بعد ما فهمنا دوكر، تعالى نشوف إزاي بنتحكم في الأوامر دي جوه كوبرنيتس (ملفات YAML). هنا الأسامي بتختلف شوية، فركز معايا! 🤓

📝 ترجمة المصطلحات (من Docker لـ K8s)

في ملف الـ Pod YAML، الحقول اسمها مختلف عن الـ Dockerfile:

في Dockerfile في Kubernetes YAML الوظيفة
ENTRYPOINT command الأمر الأساسي
CMD args المعاملات (Arguments)
⚠️ خد بالك

التسمية مربكة شوية! الـ command في K8s بيقابل ENTRYPOINT في Docker، مش CMD! متتلخبطش بينهم.

💻 مثال عملي YAML

لو عايزين نشغل كبسولة بتنام 10 ثواني (بدل 5 الافتراضية):

apiVersion: v1 kind: Pod metadata: name: ubuntu-sleeper-pod spec: containers: - name: ubuntu-sleeper image: ubuntu-sleeper command: ["sleep2.0"] # بيغير ENTRYPOINT args: ["10"] # بيغير CMD

الدرس 3

🗺️ خرائط الإعدادات (ConfigMaps)

في أي أبلكيشن، بتحتاج متغيرات زي (لون الخلفية، رابط الداتابيز، بيئة العمل Dev/Prod). مش منطقي نكتب الحاجات دي جوه الكود ونبني الصورة كل شوية! هنا بيجي دور الـ ConfigMaps. 🗺️

🌌 الفكرة ببساطة

الـ ConfigMap عاملة زي ورقة الملاحظات (Notepad) اللي بتلزقها على الكبسولة من بره. الكبسولة وهي قايمة، بتقرا الورقة دي وتعرف هي شغالة بـ "لون أزرق" ولا "أخضر"، من غير ما نفتح الكبسولة نفسها ونعدل فيها.

🛸 تشبيه الفضاء

تخيل عندك "روبوت طبخ" 🤖. بدل ما تبرمجه كل يوم يطبخ إيه، أنت بتديله "ورقة" (ConfigMap) مكتوب فيها: Today_Meal: Pizza. بكره ممكن تغير الورقة وتخليها Burger، والروبوت نفسه ماتغيرش!

🛠️ إزاي بنعملها؟ (طريقتين)

1. الطريقة السريعة (Imperative):

kubectl create configmap app-config --from-literal=APP_COLOR=blue

2. الطريقة المنظمة (Declarative - YAML):

apiVersion: v1 kind: ConfigMap metadata: name: app-config data: APP_COLOR: blue APP_MODE: prod

🔗 إزاي نربطها بالكبسولة؟

بنستخدم envFrom عشان نسحب كل البيانات مرة واحدة كـ Environment Variables:

envFrom: - configMapRef: name: app-config
🔧 ركن القيادة — مصطلحات

Original Title: ConfigMaps
Decoupling: فصل الإعدادات عن الكود (عشان المرونة)

الدرس 4

🏗️ بناء صور الحاويات (Building Docker Images)

عشان تبقى كابتن محترف، مش كفاية تسوق مركبات (Containers) ناس تانية عملتها. لازم تتعلم تبني مركبتك الخاصة! 🛠️ هنا هنتعلم إزاي نكتب Dockerfile ونحوله لـ Image.

🌌 الفكرة ببساطة

الـ Dockerfile ده زي "قائمة الطلبات" والمقادير اللي بتديها للطباخ (Docker) عشان يطبخلك الأكلة (Image). كل سطر في الملف بيضيف طبقة (Layer) جديدة للأكلة دي.

🛸 تشبيه الفضاء

تخيل إنك بتبني بدلة فضاء:

  1. أول طبقة: القماش الأساسي (Base Image: Ubuntu)
  2. تاني طبقة: خراطيم الأكسجين (Install Python/Flask)
  3. تالت طبقة: الرموز والشعارات (Copy Source Code)
  4. رابع طبقة: زرار التشغيل (ENTRYPOINT)

📝 مكونات الـ Dockerfile

FROM ubuntu # 1. القاعدة الأساسية RUN apt-get update && install ... # 2. تسطيب البرامج COPY . /opt/source-code # 3. نقل الكود بتاعك ENTRYPOINT flask run # 4. أمر التشغيل
💡 معلومة طياري

كل أمر RUN أو COPY بيعمل Layer جديدة. لو عدلت في سطر واحد، دوكر ذكي وهيعيد بناء السطر ده واللي تحته بس، مش الملف كله! (Caching).

🔧 ركن القيادة — مصطلحات

Build Context: الملفات اللي بتبعتها لدوكر عشان يبني منها.
Layers: الطبقات المكونة للصورة.

الدرس 5

🔐 تشفير الأسرار (Encrypting Secrets at Rest)

أخطر حاجة في الفضاء إن حد يسرق شفرات القيادة! 😱 بشكل افتراضي، كوبرنيتس بيخزن الأسرار (Secrets) في قاعدة البيانات (etcd) كنص عادي (Plaintext). كارثة لو حد وصلها! تعالى نعلمك إزاي تشفرها.

🕵️‍♂️ المشكلة فين؟

لو دخلت على قاعدة بيانات etcd وجبت أي Secret، هتلاقيه مكتوب Base64 سهل جداً أي حد يفكه. الحل: نشفر البيانات قبل ما تتكتب في الهارد ديسك (Encryption at Rest).

🛡️ خطوات التأمين

  1. إنشاء مفتاح تشفير: رقم عشوائي (32 byte) بنولده بأمر: head -c 32 /dev/urandom | base64
  2. تكوين ملف الإعدادات (EncryptionConfig): ملف YAML بنقول فيه لـ API Server لو سمحت شفر أي Secret جاي لك بالمفتاح ده.
  3. تعديل الـ API Server: بنضيف --encryption-provider-config للملف بتاعه عشان يقرا الإعدادات الجديدة.
⚠️ تحذير هام

التشفير بيطبق بس على الأسرار الجديدة. القديم هيفضل زي ما هو لحد ما تعمل عليه تحديث (Write). عشان تشفر القديم كله، لازم تعمل أمر kubectl get secrets -o json | kubectl replace -f -.

🔧 ركن القيادة — مصطلحات

Encryption at Rest: التشفير أثناء التخزين (على الهارد).
Etcd: مخزن بيانات كوبرنيتس (قلب النظام).

الدرس 6

🌡️ متغيرات البيئة (Environment Variables)

أحياناً بتحتاج تقول للكبسولة معلومة سريعة وهي بتقوم، زي "أنتِ شغالة في بيئة تجريبية ولا حقيقية؟". دي بنسميها متغيرات البيئة. 🌡️

🛠️ طرق التعريف Different Ways

1. تعيين مباشر (Direct):

env: - name: APP_COLOR value: pink # قيمة ثابتة

2. من ConfigMap (Recommended):

env: - name: APP_COLOR valueFrom: configMapKeyRef: name: my-config key: app_color

3. من Secret (للبيانات الحساسة):

env: - name: DB_PASSWORD valueFrom: secretKeyRef: name: my-secret key: password
🛸 تشبيه الفضاء

زي بدلة الفضاء، ممكن تظبط درجة الحرارة (Direct) قبل ما تخرج. أو ممكن تربطها بنظام التحكم المركزي (ConfigMap) هو يظبطها أوتوماتيك حسب المكان اللي أنت فيه.

🔧 ركن القيادة — مصطلحات

ValueFrom: هات القيمة من مصدر تاني (مش مكتوبة هنا).

الدرس 7

🎯 اختيار العقد (Node Selectors)

عندك محطة فضاء فيها سفن كبيرة (Nodes قوية) وسفن صغيرة (Nodes ضعيفة). أكيد مش هتحط حمولة تقيلة على سفينة صغيرة! 🚢 هنا بيجي دور Node Selector عشان نختار السفينة الصح.

🌌 الفكرة ببساطة

أبسط طريقة عشان تقول للكبسولة "روحي اشتغلي على السيرفر الكبير" هي الـ nodeSelector. بندي للسيرفر (Node) علامة (Label) زي size=Large، ونقول للكبسولة دوري على العلامة دي.

🛠️ الخطوات

  1. تسمية الـ Node:
    kubectl label nodes node01 size=Large
  2. تعديل الـ Pod:
    spec: nodeSelector: size: Large
⚠️ عيب الطريقة دي

طريقة سهلة بس "غبية" شوية. 😅 مينفعش تقول مثلاً "عايز Large أو Medium". يا Large يا بلاش! عشان كده عملنا الـ Node Affinity (الدرس الجاي).

🔧 ركن القيادة — مصطلحات

Label: استيكر بنلزقه على الـ Node عشان نميزه.
Selector: الفلتر اللي بيختار الاستيكر ده.

الدرس 8

🧲 جاذبية العقد (Node Affinity)

الـ Affinity يعني "الجاذبية" أو "الميل". 🧲 دي النسخة المتطورة من الـ Node Selector. بتخليك تعمل شروط معقدة وذكية جداً لتوجيه الكبسولات.

🌌 المميزات الجديدة

  • أو (OR): ممكن تقول "عايز Node حجمه Large أو Medium".
  • النفي (NOT): "أي Node ماعدا الـ Small".
  • المرونة (Soft Rules): "حاول تلاقي Large، لو مفيش.. مش مشكلة، شغلي في أي حتة" (Preferred).

📝 أنواع الـ Affinity

اللغة في YAML معقدة شوية، بس ركز في الجملتين دول:

🛸 أنواع القواعد

1. Required during scheduling: (لازم ولابد) 😤
لو الشرط مش موجود، الكبسولة مش هتشتغل خالص (Pending).

2. Preferred during scheduling: (ياريت لو ينفع) 🥺
لو الشرط مش موجود، الكبسولة هتشتغل عادي في مكان تاني.

💻 مثال عملي (YAML)

affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: size operator: In values: - Large - Medium
🔧 ركن القيادة — مصطلحات

IgnoredDuringExecution: يعني لو الـ Node اتغيرت صفاته والكبسولة شغالة، سيبها شغالة متطردهاش.
Operator In: يعني القيمة تكون واحدة من القائمة.

الدرس 9

🛡️ أمان دوكر (Docker Security Prerequisites)

قبل ما نتكلم عن أمان كوبرنيتس، لازم نفهم أمان "المركبة" نفسها (Docker Container). هل الكبسولة معزولة فعلاً عن المحطة؟ وإيه صلاحيات القائد جواها؟ 🤔

🌌 العزل (Isolation)

الكبسولة مش Virtual Machine كاملة. هي بتشارك "نواة" (Kernel) النظام مع السيرفر الأصلي. بس بنستخدم سحر اسمه Namespaces عشان نعزلها.

🛸 تشبيه الفضاء

تخيل إنك في غرفة في فندق (Namespace). أنت حر جوه الغرفة، بس مسموحلكش تخرج للصالة وتتحكم في كهرباء الفندق كله (Kernel)! مع إنك في نفس المبنى.

👑 الصلاحيات (Capabilities)

بشكل افتراضي، الـ Container بيشتغل بـ Root (المدير). بس "مدير مقيد"! دوكر بيسحب منه صلاحيات خطيرة (زي تعديل الساعة، أو التحكم في الشبكة الرئيسية) باستخدام Linux Capabilities.

docker run --cap-add MAC_ADMIN ubuntu # إضافة صلاحية
docker run --cap-drop KILL ubuntu # سحب صلاحية
⚠️ تحذير

إياك تستخدم --privileged إلا للضرورة القصوى! ده بيدي الكبسولة مفاتيح الفندق كله، وممكن تدمر السيرفر الأساسي.

🔧 ركن القيادة — مصطلحات

Namespace: حدود العزل (زي الغرف).
Capabilities: كروت الصلاحية (مسموح لك تعمل إيه).

الدرس 10

🔋 إدارة الموارد (Resource Requirements)

في محطة الفضاء، الطاقة والأكسجين (CPU & RAM) محدودين. مينفعش كبسولة واحدة تستهلك كل حاجة وتخنق الباقيين! 😵 لازم نحدد لكل كبسولة "حصتها" بالظبط.

🌌 الفرق بين Requests و Limits

🛸 تشبيه الفضاء

1. Requests (الطلب): زي الحجز في مطعم.
"أنا محتاج ترابيزة لشخصين" (2GB RAM). كوبرنيتس هيدور على Node فيها مكان فاضي للكمية دي ويحطك فيها. ده "الحد الأدنى" المضمون ليك.

2. Limits (الحد الأقصى): زي سعة المعدة.
"مقدرش آكل أكتر من 4 وجبات" (4GB RAM). لو حاولت تستهلك أكتر من كده، كوبرنيتس هيتدخل فوراً!

⚠️ ماذا يحدث لو تعدينا الحدود؟

  • CPU: لو طلبت أكتر من الـ Limit، النظام "هيخنقك" (Throttling). هتبقى بطيء جداً، بس مش هتموت.
  • Memory (RAM): لو طلبت أكتر من الـ Limit، مفيش تفاهم! النظام هيقتلك فوراً (OOM Killed - Out Of Memory). ☠️

💻 مثال عملي YAML

resources: requests: memory: "64Mi" # الحد الأدنى للتشغيل cpu: "250m" # ربع نواة (0.25) limits: memory: "128Mi" # سقف الاستهلاك cpu: "500m" # نصف نواة (0.5)
🔧 ركن القيادة — مصطلحات

OOM Killed: الكبسولة ماتت بسبب استهلاك الذاكرة الزائد.
Milli-cpu (m): وحدة قياس المعالج (1000m = 1 Core).

الدرس 11

🕵️‍♂️ الأسرار (Secrets)

تكلمنا قبل كده عن ConfigMap للبيانات العادية. طب لو عندك "باسورد الداتابيز" أو "مفاتيح API"؟ مينفعش تحطها في ورقة (ConfigMap) وتلزقها على الحيطة! محتاجين خزنة (Secret). 🔐

🌌 الفرق الجوهري

الـ Secret هو توأم الـ ConfigMap، بس بيشيل بيانات حساسة. البيانات بتتشفر (Encoded Base64) عشان متبقاش مقروءة بالعين المجردة.

🛠️ طرق الاستخدام

ممكن تستخدم الـ Secret بنفس طرق الـ ConfigMap بالظبط:

  1. كبسولة بيئة (Environment Variable): الكبسولة تفتح الخزنة وتاخد الباسورد في الذاكرة.
  2. ملف (Volume Mount): الكبسولة تلاقي ملف سري جواها مكتوب فيه الباسورد.
# تعريف Secret في الـ Pod env: - name: DB_PASSWORD valueFrom: secretKeyRef: name: my-secret key: password
💡 ملحوظة أمنية

تذكر إن Base64 مش تشفير حقيقي! أي حد معاه الـ Code يقدر يفكه ويرجعه نص عادي. عشان كده لازم تفعل Encryption at Rest (اللي شرحناه في الدرس 5).

الدرس 12

👮 سياق الأمان (Security Contexts)

مين اللي سايق الكبسولة؟ ومسموح له يلمس إيه؟ الـ Security Context هو "البطاقة الشخصية" وتصريح العمل للعملية (Process) اللي شغالة جوه الكبسولة.

🌌 أهم الإعدادات

  • runAsUser: تحديد هوية المستخدم (UID). مثلاً، بدلاً من Root (0)، نستخدم مستخدم عادي (1000).
  • fsGroup: تحديد "المجموعة" (Group) اللي بتمتلك الملفات المشتركة (Volumes).
🛸 تشبيه الفضاء

لو سبت الكبسولة من غير تحديد، هتشتغل بـ Root (القائد العام). وده خطر! لو حد اخترق الكبسولة، ممكن يسيطر على المحطة كلها. الأفضل نخليها تشتغل بـ "عامل نظافة" (Limited User) عشان صلاحياته تكون محدودة.

securityContext: runAsUser: 1000 runAsGroup: 3000 fsGroup: 2000
الدرس 13

🤖 حساب الخدمة (Service Account)

البشر (أنا وأنت) ليهم "User Account" يدخلوا بيه على الكلاستر. طب الروبوتات والبرامج (زي Jenkins أو Prometheus)؟ 🤖 دول بنعملهم Service Account.

🌌 الفكرة ببساطة

أي كبسولة بتشتغل في كوبرنيتس، لازم يكون معاها "هوية" عشان تقدر تكلم الـ API Server. لو محددتش هوية، كوبرنيتس أوتوماتيك بيديها هوية اسمها default (صلاحياتها معدومة تقريباً).

🛠️ إزاي نستخدمها؟

  1. نعمل حساب جديد: kubectl create serviceaccount my-robot
  2. ندي الكبسولة الحساب ده:
    spec: serviceAccountName: my-robot
💡 معلومة

الـ Service Account بيتم ترجمته لـ Token (تصريح مرور) بيتحط جوه الكبسولة أوتوماتيك. البرنامج اللي جوه بيستخدم الـ Token ده عشان يكلم الكلاستر.

🔧 ركن القيادة — مصطلحات

User Account: للبشر (Global).
Service Account: للآلات (Namespaced).

ملحق 1

🦟 الطارد والمتحمل (Taints & Tolerations)

اتكلمنا عن إزاي الكبسولة تختار الـ Node (بالـ Affinity). دلوقتي العكس! إزاي الـ Node هو اللي يختار مين ينزل عليه ومين لأ؟ 🛑

🌌 تشبيه الحشرات (رسمي من كوبرنيتس)

🦠 الناموس والمبيد

تخيل الـ Node هو "شخص" رش نفسه بمبيد حشري (Taint). كل الحشرات (Pods) هتهرب منه ومش هتقدر تقف عليه. إلا لو فيه حشرة لابسة "قناع واقي" (Toleration)، دي بس اللي هتقدر تستحمل المبيد وتقف عليه.

🛠️ إزاي نستخدمها؟

1. رش المبيد (Taint the Node):

kubectl taint nodes node1 app=blue:NoSchedule

كده أي كبسولة "طبيعية" مش هتنزل على node1.

2. لبس القناع (Add Toleration to Pod):

tolerations: - key: "app" operator: "Equal" value: "blue" effect: "NoSchedule"

كده الكبسولة دي "متحملة" للون الأزرق، فتقدر تنزل على الـ Node ده.

🔧 التأثيرات (Effects)
  • NoSchedule: ممنوع النزول (للكبسولات الجديدة).
  • PreferNoSchedule: يفضل بلاش (بس لو مفيش مكان غيره، ماشي).
  • NoExecute: طرد فوري! لو كبسولة شغالة ومش معاها التصريح، تترمي بره فوراً.
ملحق 2

⚔️ الطرد vs الجذب (Taints vs Node Affinity)

سؤال مهم: إمتى نستخدم ده وإمتى نستخدم ده؟ الإجابة: عشان تخصص سيرفر معين لفريق معين 100%، لازم تستخدم الاثنين مع بعض! 🤝

🌌 السيناريو الكامل

تخيل عندنا سيرفر "أحمر" 🔴 مخصص للفريق الأحمر بس.

الأداة الوظيفة النتيجة
Taint (على السيرفر) "ممنوع دخول أي حد مش أحمر" بيمنع الغرباء (الأخضر والأزرق)
Node Affinity (على الكبسولة) "وديني ورا السيرفر الأحمر" بيخلي كبسولتنا تروح هناك (بدل ما تروح سيرفر فاضي تاني)
💡 الخلاصة

Taints بتبعد الوحشين.
Affinity بتجذب الحلوين.
استخدم الاثنين عشان تضمن إن سيرفرك "محجوز بالكامل" ليك.
