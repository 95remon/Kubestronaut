🚀 المهمة 3: الإعدادات (Configuration)

يا هلا بيك يا رائد الفضاء! ⚓ في المهمة دي هنتعلم إزاي نتحكم في السفن بتاعتنا: ConfigMaps, Secrets, Service Accounts, وكمان تظبيط الموارد!

🛠️ 1. Docker & Container Basics

🛡️

1. Docker Security Prerequisites

يا هلا! قبل ما نغوص في أمان Kubernetes، محتاجين نراجع شوية أساسيات عن الأمان في Docker. لو إنت "بريمو" في Docker ممكن تعدي الدرس ده، بس المراجعة مش هتضر! 😉

عزل العمليات (Process Isolation)

تخيل السيرفر بتاعك (Host) شغال عليه حاجات كتير: متصفح، SSH، وكمان Docker Daemon. لما تيجي تشغل كونتينر Ubuntu وتقوله "نام ساعة" بالأمر ده:

BASH
docker run ubuntu sleep 3600

الكونتينرات خفيفة (Lightweight) لأنها بتشارك نفس الـ Kernel بتاع الـ Host. السر هنا في حاجة اسمها Linux Namespaces. دي اللي بتخلي الكونتينر شايف نفسه "لوحده" في الدنيا.

جوا الكونتينر، لو بصيت على الـ Processes، هتلاقي الأمر sleep واخد PID 1. لكن لو بصيت من برا (على الـ Host)، هتلاقيه واخد PID مختلف تماماً.

مين المستخدم؟ (User Context)

بشكل افتراضي، Docker بيشغل العمليات جوه الكونتينر بـ Root. وده ممكن يكون خطر لو الكونتينر حصله اختراق! 😱

💡 نصيحة محترف

دايماً حاول تشغل تطبيقاتك بـ Non-Root User. ممكن تحدد ده وأنت بتعمل run بالأمر --user=1000، أو الأفضل تحدده جوه الـ Dockerfile نفسه.

صلاحيات الـ Root (Calculated Capabilities)

هل الـ Root جوه الكونتينر زي الـ Root برا؟ لأ طبعاً! Docker بيقصقص ريش الـ Root اللي جوه الكونتينر باستخدام Linux Capabilities. يعني مثلاً، الـ Root اللي جوه مش مسموح له يعمل Reboot للسيرفر الحقيقي.

📦

2. Define, Build & Modify Images

تعالوا نتعلم إزاي نبني Docker Image بنفسنا. هنعمل تطبيق Python Flask بسيط ونحطه في كونتينر. الموضوع ده مهم جداً عشان مش كل حاجة هتلاقيها جاهزة على Docker Hub.

قبل الـ Dockerfile

لو هتعمل الموضوع يدوي، كنت هتحتاج: تنزل Ubuntu، تعمل Update، تنزل Python و pip، تنسخ الكود، وتشغل السيرفر. لفة طويلة! 😰

الـ Dockerfile السحري

الـ Dockerfile هو ورقة التعليمات اللي بتقول لـ Docker يعمل إيه بالظبط. بص على المثال ده:

Dockerfile
FROM ubuntu
RUN apt-get update && apt-get -y install python python-setuptools python-dev
RUN pip install flask flask-mysql
COPY . /opt/source-code
ENTRYPOINT FLASK_APP=/opt/source-code/app.py flask run --host=0.0.0.0

🥪 تشبيه الطبقات (Layers)

كل سطر في الـ Dockerfile بيعمل "طبقة" (Layer) جديدة في الصورة. لو غيرت سطر واحد بس في الآخر، Docker ذكي كفاية إنه يعيد بناء الطبقات اللي اتغيرت بس، ويستخدم القديم من الـ Cache. زي لما تكون بتبني عمارة، مش بتهد الأساسات عشان تغير لون الدهان في الدور الأخير!

بناء الصورة (Build)

عشان تحول الملف ده لـ Image، بتستخدم الأمر:

docker build -t my-custom-app .
⌨️

3. Commands & Arguments in Docker

في الحتة دي هنتعلم الفرق بين CMD و ENTRYPOINT. دي من أكتر الحاجات اللي بتلخبط، بس هنفك شفرتها سوا. 😉

حياة الكونتينر وقراره

الكونتينر بيموت 💀 أول ما العملية الأساسية اللي جواه تخلص. يعني لو مشغل sleep 5، الكونتينر هيصحى 5 ثواني وبعدين يقفل.

CMD: الأمر الافتراضي

التعليمة CMD في الـ Dockerfile بتحدد الأمر اللي هيشتغل "لو مفيش حد قال حاجة تانية".

FROM ubuntu
CMD ["sleep", "5"]

لو شغلت الكونتينر كده docker run my-image، هينام 5 ثواني. لكن لو قولت docker run my-image sleep 10، الـ Docker هينسى الـ CMD القديم ويسمع كلامك الجديد.

ENTRYPOINT: الثابت الراسخ

الـ ENTRYPOINT بقى زي "اسم العيلة"، حاجة ثابتة مش بتتغير بسهولة. أي حاجة تكتبها بعد اسم الصورة في الـ Run Command بتتحط كـ Arguments للـ Entrypoint.

Dockerfile
FROM ubuntu
ENTRYPOINT ["sleep"]
CMD ["5"]

في الحالة دي:

  • docker run my-image ➡️ هينفذ sleep 5
  • docker run my-image 10 ➡️ هينفذ sleep 10 (الـ 10 بدلت الـ 5)
☸️

4. Commands & Arguments in Kubernetes

دلوقتي إحنا عرفنا بيتعملوا إزاي في Docker، طب في Kubernetes؟ بنستخدم command و args في ملف الـ YAML.

⚠️ خريطة الترجمة (مهمة جداً!)

خد بالك من الترجمة دي عشان متتلخبطش:

  • Docker: ENTRYPOINT ➡️ Kubernetes: command
  • Docker: CMD ➡️ Kubernetes: args

مثال عملي

لو عندنا صورة بتعمل sleep وعايزين نغير المدة لـ 10 ثواني في الـ Pod:

YAML
apiVersion: v1
kind: Pod
metadata:
  name: ubuntu-sleeper-pod
spec:
  containers:
    - name: ubuntu-sleeper
      image: ubuntu-sleeper
      args: ["10"]  <-- دي بتبدل الـ CMD في الدوكر

ولو عايز تغير الـ Entrypoint نفسه (تستخدم أمر تاني خالص)، هتستخدم command:

command: ["sleep2.0"]
args: ["10"]
🧪

5. Lab Solution: Commands & Arguments

تعالوا نطبق عملي ونشوف شوية سيناريوهات ممكن تقابلها.

1. استكشاف الـ Pod

عشان تعرف الـ Pod ده شغال بأمر إيه، استخدم:

kubectl describe pod ubuntu-sleeper

هتلاقي في الـ Output خانة Command وخانة Args.

2. تعديل Pod شغال؟

لو حاولت تعمل kubectl edit pod وغيرت في الـ Command، غالباً هتضرب في وشك! 🚫 كوبرنيتس مش بيسمح بتغيير خصائص معينة في الـ Pod وهو شغال.

الحل: عدل ملف الـ YAML عندك، وبعدين اعمل:

kubectl replace --force -f pod.yaml

ده هيمسح القديم ويعمل واحد جديد بالتعديلات.

لما تستخدم kubectl run، استخدم -- عشان تفصل بين أوامر kubectl وأوامر الكونتينر:

kubectl run webapp --image=color -- --color=green

🌱

6. Environment Variables

عشان تخلي تطبيقك "فليكسيبيل" (Flexible) ويشتغل في أي بيئة (Dev, Test, Prod)، لازم تستخدم متغيرات البيئة. 🌍

الطريقة المباشرة (Direct)

ممكن تحط المتغيرات دي جوه ملف الـ Pod مباشرةً. طريقة سهلة وسريعة بس مش عملية في المشاريع الكبيرة.

YAML
env:
  - name: APP_COLOR
    value: pink

الطريقة المحترفة (Decoupled)

الأشيك إنك تستخدم ConfigMaps أو Secrets. كده بتفصل الكود عن الإعدادات، وده هو "الصح". 👌

env:
  - name: APP_COLOR
    valueFrom:
      configMapKeyRef:
        name: my-config
        key: app_color
🗺️

7. ConfigMaps

الـ ConfigMap هو عبارة عن قاموس (key-value pairs) بنخزن فيه إعدادات التطبيق اللي مش سرية. زي لون الخلفية، عنوان الداتا بيز (Host)، أو الـ Port.

إزاي تعمل ConfigMap؟

في طريقتين: Imperative (بالأمر السريع) و Declarative (بملف YAML).

1. الأمر السريع (Imperative)

kubectl create configmap app-config --from-literal=APP_COLOR=blue

2. ملف YAML (Declarative)

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_COLOR: blue
  APP_MODE: prod

إزاي تستخدمه في الـ Pod؟

ممكن تحقن كل المتغيرات مرة واحدة باستخدام envFrom:

envFrom:
  - configMapRef:
      name: app-config

كده أي حاجة في الـ ConfigMap بقت Environment Variable جوه الكونتينر بتاعك. سحر ولا مش سحر؟ ✨

🧪

8. Lab Solution: ConfigMaps

في اللاب ده، شوفنا إزاي نغير لون التطبيق من غير ما نلمس كود التطبيق نفسه. كل اللي عملناه إننا غيرنا القيمة في الـ ConfigMap.

💡 تلميح

9. Secrets

الـ Secrets زي الـ ConfigMaps بالظبط، بس مخصصة للحاجات الحساسة: باسووردات، مفاتيح API، شهادات SSL. 🗝️

التشفير (Encoding)

كوبرنيتس بيخزن الـ Secrets بصيغة Base64. خد بالك ده مش تشفير حقيقي، ده مجرد "ترميز". أي حد معاه الـ Base64 يقدر يرجعه لأصله بسهولة.

BASH
echo -n 'password123' | base64
# Output: cGFzc3dvcmQxMjM=

ولما تيجي تعمل ملف Secret YAML، بتحط القيم المتكودة دي:

data:
  DB_Password: cGFzc3dvcmQxMjM=

⚠️ تحذير أمني

ماتحطش ملفات الـ Secrets YAML في الـ Git Repo بتاعك وهي فيها البيانات الحقيقية! دي كارثة أمنية. استخدم أدوات زي Helm Secrets أو Sealed Secrets، أو متعملش Commit للملفات دي أصلاً.

🧪

10. Lab Solution: Secrets

في اللاب ده، التطبيق كان ضارب Error لإنه مش عارف يوصل للداتا بيز. السبب؟ مكنش لاقي اليوزر والباسوورد.

حلينا المشكلة بإننا عملنا Secret اسمه db-secret وحطينا فيه الـ Credentials، وبعدين ربطناه بالـ Pod باستخدام secretRef. بعدها التطبيق اشتغل تمام واللون الأخضر ظهر! ✅

🔒

11. Demo: Encryption at Rest

قولنا إن الـ Secrets بتتسجل Base64، يعني مش متشفره في الـ etcd (قاعدة بيانات كوبرنيتس). لو حد وصل للـ etcd، هيقدر يشوف كل أسرارك! 😱

عشان كده، لازم نفعل خاصية Encryption at Rest.

إزاي بتشتغل؟

  1. بنعمل ملف إعدادات (EncryptionConfiguration) بنحدد فيه مفتاح التشفير ونوعه (مثلاً AES-CBC).
  2. بنعدل الـ Kube-API Server عشان يستخدم الملف ده.

بعد ما تفعلها، أي Secret جديد هتعمله هيتشفر أوتوماتيك وهو بيتكتب في الـ etcd. ولو بصيت عليه بأداة etcdctl هتلاقيه "شخابيط" مش مفهومة، وده المطلوب! 😎

🔐 3. Security & Accounts

👮‍♂️

12. Security Contexts

مين بالظبط اللي بيشغل الكونتينر بتاعك؟ Root ولا مستخدم عادي؟ الـ Security Context هو اللي بيحدد قواعد اللعبة دي. 🤔

Docker vs Kubernetes

في Docker كنا بنقول --user=1001. في كوبرنيتس، عندنا مرونة أكتر. نقدر نحدد القواعد على مستوى الـ Pod كله، أو على مستوى Container محدد.

⚠️ قاعدة الأولويات

لو حددت إعدادات في الـ Pod وإعدادات تانية في الـ Container، مين يكسب؟
الكونتينر يكسب! (Specific overrides General).

مثال: تشغيل بمستخدم معين

YAML
spec:
  securityContext:
    runAsUser: 1000  <-- ده للـ Pod كله
  containers:
    - name: sec-ctx-demo
      image: gcr.io/google-samples/node-hello:1.0
      securityContext:
        runAsUser: 2000  <-- ده "كلامه يمشي" على الكونتينر ده بس
        allowPrivilegeEscalation: false

قدرات اللينكس (Capabilities)

مش لازم تدي الـ Root كل الصلاحيات. ممكن تدي صلاحية واحدة بس زي NET_ADMIN لو محتاج تلعب في الشبكة، أو SYS_TIME لو محتاج تظبط الساعة.

securityContext:
  capabilities:
    add: ["NET_ADMIN", "SYS_TIME"]
🧪

في اللاب، جربنا ندخل جوه كونتينر ونشوف مين المستخدم بالأمر whoami.

تغيير المستخدم لـ 1010

عدلنا ملف الـ YAML وضفنا runAsUser: 1010. لما عملنا Apply ودخلنا تاني، لقينا النتيجة اتغيرت لـ non-root user. خطوة مهمة جداً للأمان!

تعدد الحاويات (Multi-Container Pods)

كان عندنا Pod فيه كونتينر ويب (Web) وكونتينر مساعد (Sidecar).
الـ Pod كان واخد User 1001.
الـ Web كان عنده Overwrite لـ User 1002.
النتيجة: الـ Web اشتغل بـ 1002، والـ Sidecar ورث الـ 1001 من أبوه (الـ Pod).

14. Service Accounts

في كوبرنيتس عندنا نوعين من الحسابات:

  1. User Accounts: للبني آدمين (زيي وزيك).
  2. Service Accounts (SA): للروبوتات والتطبيقات (زي Prometheus, Jenkins, أو Dashboard).

سيناريو الـ Dashboard

لو عندك تطبيق "Dashboard" عايز يكلم الـ API Server عشان يعرض الـ Pods. لازم يكون عنده "هوية" وصلاحيات. هنا بيجي دور الـ Service Account.

BASH
kubectl create serviceaccount dashboard-sa
kubectl get serviceaccount

التوكن السحري (Token)

أي SA بيتعمل، كوبرنيتس (في الإصدارات القديمة) كان بيعمله Secret فيه Token أوتوماتيك. في الإصدارات الجديدة (1.24+)، التوكن بيبقى مؤقت (Projected Volume) أو بتعمله أنت بالأمر:

kubectl create token dashboard-sa

إزاي نربطه بالـ Pod؟

بسيطة! ضيف السطر ده في مواصفات الـ Pod:

spec:
  serviceAccountName: dashboard-sa

لو معملتش كده، الـ Pod هياخد الـ default account، وده صلاحياته معدمة (غلبان يعني 😅).

🧪

📅 4. Resources & Scheduling

⚖️

16. Resource Requirements

كل Pod محتاج ياكل ويشرب (CPU & Memory). لو سبناهم من غير ضوابط، واحد بس ممكن ياكل الأخضر واليابس! 🦖

1. Requests (الحد الأدنى)

ده "أقل واجب" الـ Pod محتاجه عشان يشتغل. الكوبرنيتس بيدور على Node فيها مساحة فاضية قد الكمية دي بالظبط.

YAML
resources:
  requests:
    memory: "64Mi"
    cpu: "250m"  # ربع كور (Core)

2. Limits (الحد الأقصى)

ده السقف اللي محدش يقدر يعديه. لو الـ Pod حاول يستهلك أكتر من كده:

  • CPU: هيتعمل له Throttling (يتبطأ).
  • Memory: هيتعمل له Terminate (يموت) ويطلع Error اسمه OOMKilled. 💀
resources:
  limits:
    memory: "128Mi"
    cpu: "500m"
🧪

17. Lab Solution: Resource Limits

في اللاب ده كان عندنا فيل (Elephant Pod) بيموت كل شوية بـ OOMKilled. 🐘

المشكلة إنه كان محتاج 15MB ميموري، بس إحنا كنا محجمينه بـ 10MB بس.

الحل: زودنا الـ Limit لـ 20MB، والفيل عاش ومبسوط.

🦟

18. Taints & Tolerations

تخيل إن الـ Node راشّة مبيد حشري (Taint). مفيش أي حشرة (Pod) تقدر تقف عليها إلا لو عندها مناعة (Toleration) ضد المبيد ده. 😷

إزاي تعمل Taint للـ Node؟

BASH
kubectl taint nodes node1 app=blue:NoSchedule

أنواع التأثيرات (Effects):

  • NoSchedule: ممنوع الوقوف نهائياً (إلا لو معاك تصريح).
  • PreferNoSchedule: يفضل لأ، بس لو مفيش مكان تاني.. ماشي.
  • NoExecute: اللي واقف ومعهوش تصريح.. يطرد فوراً! ⛔

إزاي تدي الـ Pod مناعة (Toleration)؟

YAML
tolerations:
  - key: "app"
    operator: "Equal"
    value: "blue"
    effect: "NoSchedule"
🧪

20. Node Selectors

أبسط طريقة عشان تقول للـ Pod "روحي للـ Node الفلانية". بنستخدم الـ Labels.

المثال:

عايزين الـ Pod تنزل بس على الـ Nodes الكبيرة (Large).

spec:
  nodeSelector:
    size: Large

بس طبعاً دي طريقة "على قدها" ومفيهاش مرونة (يا أبيض يا إسود).

❤️

21. Node Affinity

النسخة "المطورة" من الـ Node Selectors. فيها شروط معقدة زي (OR, NOT, Exists).

أنواع الـ Affinity:

  • Required: لازم ولابد (زي الـ Node Selector بس أقوي).
  • Preferred: "يا ريت" لو موجود، لو مش موجود خلاص مش مشكلة. (مرونة عالية). 
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: size
          operator: In
          values:
          - Large
          - Medium

هنا بنقوله: الـ Pod دي تنزل على الـ Large أو Medium. (شفت المرونة؟ 😉)

🧪

وعملنا Deployment "أحمر" ينزل بس على الـ Controlplane Node.

23. Taints vs Node Affinity

إمتى نستخدم ده وإمتى نستخدم ده؟ الخلاصة:

الخاصية Taints & Tolerations Node Affinity
الوظيفة بتقول للـ Pods "ابعدوا عني!" ⛔ بتقول للـ Pods "تعالوا عندي!" 🧲
الضمان تضمن إن الـ Node محدش غريب يجي عليها. تضمن إن الـ Pod تروح للمكان الصح.
